1. Introduction
1.1 Purpose
This document specifies the functional and non-functional requirements for the One Medical platform — a physiotherapy and rehabilitation recovery ecosystem consisting of a patient-facing mobile application, a public marketing website, and an admin/therapist web console, backed by a microservices backend. It is intended for backend engineers, mobile/web developers, QA, and DevOps to build a production-grade system without ambiguity.
1.2 Scope
The system enables patients to discover physiotherapists, book appointments, follow assigned recovery programs with guided exercises, track recovery progress, manage medical records, and pay for consultations. Clinic staff (therapists/admins) manage patients, appointments, recovery programs, exercise libraries, payments/invoicing, and view analytics/reports. The marketing website serves as the top-of-funnel acquisition channel that feeds into the same booking pipeline.

2. Overall Description
2.1 Product Perspective
One Medical is a new, self-contained product composed of three client applications sharing one backend platform:
Patient Mobile App — React Native (iOS + Android), consumed by patients.
Admin/Therapist Web Console — React.js SPA, used by clinic admins, receptionists, and therapists.
Marketing Website — React.js (SSR/SSG via Next.js) for SEO, public and unauthenticated.
All three clients talk to a single API Gateway, which routes requests to independent backend microservices. Each service owns its own MongoDB database (database-per-service pattern) — no service reaches into another service's database directly.
2.2 Product Functions (Summary)
Patient & staff authentication with OTP verification and role-based access.
Therapist discovery, appointment booking, rescheduling and cancellation with real-time slot availability.
Recovery program authoring, assignment, exercise tracking and progress scoring.
Medical record and report storage (scans, MRI, clinical notes).
Payments, invoicing, refunds, and therapist payouts.
Notifications (push, SMS, email) for appointments, reminders, and recovery milestones.
Admin analytics: patient, therapist, revenue and recovery-outcome reporting.

3. System Architecture (Microservices)
3.1 Architecture Style
The backend follows a microservices architecture with one API Gateway and four independently deployable domain services, each owning its own MongoDB database. Services communicate synchronously via REST (through the gateway or direct service-to-service calls for internal reads) and asynchronously via an event bus (RabbitMQ) for cross-domain side effects such as notifications, so that no service is blocked waiting on another.
3.2 Service Breakdown
3.2.1 API Gateway
Single entry point for all three clients. Responsibilities:
Request routing to the correct downstream microservice by path prefix.
JWT verification and RBAC enforcement before forwarding requests.
Rate limiting (per-IP and per-user) and request throttling.
Response aggregation for composite views (e.g. patient home screen needs data from Scheduling + Clinical services).
Centralized request logging, correlation IDs, and API versioning (/api/v1/...).
CORS policy enforcement and TLS termination.
3.2.2 Identity & User Service
Owns authentication and all user identity data for patients, therapists, and staff.
Registration, login, OTP generation/verification, password reset.
JWT access/refresh token issuance and rotation.
Role and permission management (RBAC).
Patient profile, medical intake, and therapist profile (specialization, qualifications, availability template) management.
Owns database: identity_db
3.2.3 Scheduling & Appointment Service
Owns therapist availability and the full appointment lifecycle.
Availability slot generation from therapist templates + exceptions (leave, holidays).
Appointment booking with atomic slot-locking to prevent double booking.
Reschedule, cancellation, no-show and completion state transitions.
Publishes appointment.created / appointment.cancelled / appointment.completed events.
Owns database: scheduling_db
3.2.4 Clinical & Recovery Service
Owns clinical content and patient recovery data.
Exercise library (CRUD), recovery program authoring and assignment.
Session logging, recovery score computation, milestone tracking.
Medical records/reports metadata (files stored in S3; service stores references).
Owns database: clinical_db
3.2.5 Payment & Billing Service
Owns all monetary transactions.
Payment intent creation, gateway webhook handling, invoice generation.
Refunds and therapist payout computation.
Publishes payment.succeeded / payment.failed / refund.issued events.
Owns database: payments_db
3.2.6 Asynchronous Notification Worker (shared infrastructure, not a REST-facing service)
A lightweight consumer subscribed to RabbitMQ topics published by the four services. It sends push (FCM), SMS, and email notifications. It is not counted as a fifth REST microservice — it has no public API and exists purely to decouple notification delivery from the request/response cycle.
3.3 Inter-Service Communication
Client → Gateway → Service: synchronous REST/JSON over HTTPS for all user-initiated actions.
Service → Service (synchronous): only for read-only lookups the gateway cannot aggregate cheaply (e.g. Scheduling Service validates therapistId exists by calling Identity Service's internal /internal/therapists/:id endpoint, protected by a service-to-service API key, never exposed publicly).
Service → Broker → Worker (asynchronous): RabbitMQ topic exchange for events (appointment confirmed, payment succeeded, recovery milestone hit) — decouples notification delivery and analytics indexing from the originating request.
No service ever queries another service's database directly — this is enforced architecturally by giving each service its own MongoDB connection string and network policy.
3.4 High-Level Architecture Diagram (described)
[Patient App / Web Console / Website] → HTTPS → [API Gateway (auth, routing, rate-limit)] → [Identity Service | Scheduling Service | Clinical Service | Payment Service] each with its own MongoDB → services publish domain events → [RabbitMQ] → [Notification Worker] → FCM / SMS / Email. Shared Redis cluster used for caching, rate-limit counters and distributed locks (slot booking).

8. Critical Flow Specifications
8.1 Appointment Booking Flow
Patient searches therapists (Gateway → Scheduling Service enriches Identity Service therapist list with next-available slot).
Patient selects therapist, date and time slot.
Scheduling Service acquires a Redis lock for {therapistId, date, startTime}; on success creates appointment in 'pending_payment' with a 10-minute expiry (TTL index in MongoDB).
Gateway calls Payment Service to create a gateway order tagged with the appointment ID as idempotency key.
Client completes payment via gateway SDK; gateway sends an async webhook to Payment Service.
Payment Service verifies the webhook signature, marks the transaction 'captured', publishes payment.succeeded event.
Scheduling Service (subscribed to payment.succeeded) transitions the appointment to 'confirmed' and releases the slot lock.
Notification Worker (subscribed to appointment confirmed) sends push/SMS/email confirmations to patient and therapist.
If payment is not completed within 10 minutes, a scheduled job expires the appointment back to 'cancelled' and the slot becomes bookable again.
8.2 Recovery Session Logging Flow
Patient opens 'Today's Session' — mobile app fetches the patient's active program's exercises scheduled for the current day from Clinical Service (cached locally for offline access).
Patient marks exercises complete and enters pain level (0–10).
On submit, app POSTs a session_log; if offline, the request is queued in local storage and retried on reconnect (idempotent via a client-generated sessionLogId).
Clinical Service recalculates the recoveryScore using the weighted formula (FR-3.5) and updates patient_programs.
If painLevel ≥ threshold for 2 consecutive sessions, Clinical Service publishes a clinical.alert event consumed by the Notification Worker to alert the assigned therapist.
8.3 Payment Webhook Reliability
Webhook endpoint verifies the gateway's HMAC signature before trusting the payload.
Webhook processing is idempotent keyed by gatewayPaymentId — replayed webhooks (gateway retries) are safely ignored if already processed.
If Payment Service is down when a webhook arrives, the gateway's own retry-with-backoff (typically up to 24h) covers delivery; a reconciliation job also polls the gateway's Orders API hourly for any order stuck in 'created' > 15 minutes to catch missed webhooks.

Maintainability
Each service has independent CI/CD, versioned OpenAPI spec, and >80% unit test coverage on business logic (booking rules, recovery-score calculation, payment state machine).
Observability
Structured JSON logs with correlation ID propagated from the gateway through all downstream calls; metrics exported to Prometheus; error tracking via Sentry.
10. Security Requirements
Passwords hashed with bcrypt (cost factor 12); OTPs stored as salted hashes, never plaintext.
JWT access tokens short-lived (15 min); refresh tokens rotated on every use and revocable (stored as a jti list per user for logout-everywhere support).
All inputs validated at the gateway and again at the service layer (Zod/Joi schemas) — defense in depth against malformed/malicious payloads.
Rate limiting: OTP requests (3/10 min/number), login attempts (5/15 min/account, then temporary lockout), general API (100 req/min/IP at the gateway).
RBAC enforced centrally at the gateway using the role claim in the JWT; services additionally re-check ownership (e.g. a patient can only fetch their own medical records) to prevent IDOR (Insecure Direct Object Reference) vulnerabilities.
File uploads restricted by MIME type and size (25 MB), scanned for malware before being persisted to S3, and served only via short-lived pre-signed URLs — never public S3 URLs.
Payment webhook endpoints verify gateway signatures; all other webhook/internal endpoints protected by a service-to-service API key not exposed to any client.
Full audit log (append-only collection) for medical-record access, role changes, refunds and account deletions.
OWASP Top 10 mitigations: parameterized queries via Mongoose (no raw query injection), Helmet.js security headers, CSRF protection on cookie-based web sessions, dependency vulnerability scanning (npm audit / Snyk) in CI.

Redis distributed lock ensures only the first request proceeds; the second receives 409 SLOT_ALREADY_LOCKED and is shown refreshed availability.
Patient closes app mid-payment
Appointment remains 'pending_payment' with a 10-minute TTL; a background job auto-cancels and releases the slot if payment never completes.
Payment succeeds at the gateway but the confirmation webhook is delayed/lost
Hourly reconciliation job polls the gateway for orders stuck 'created' beyond 15 minutes and corrects local state; patient sees 'confirming' status in-app in the interim, not a false failure.
OTP entered incorrectly 5 times
Account is temporarily locked from OTP verification for 15 minutes; user is shown a clear cooldown message, not a generic error.
Refresh token reused after rotation (token theft indicator)
All refresh tokens for that user are revoked immediately and the user is forced to re-authenticate on all devices.
Therapist cancels an already-confirmed, paid appointment
System auto-initiates a full refund, notifies the patient, and surfaces the freed slot back into availability.
Patient attempts to access another patient's medical record via a guessed ID
Service-level ownership check returns 403 FORBIDDEN regardless of a valid JWT — never relies on the client not guessing IDs.
Mobile app goes offline mid-exercise-session logging
Log is queued locally with a client-generated idempotency key and retried on reconnect; duplicate submits are ignored server-side.
Large medical file upload exceeds size/type limits
Rejected client-side pre-upload and re-validated server-side with a specific FILE_TOO_LARGE / UNSUPPORTED_TYPE error code.
Therapist double-books themselves across two devices/tabs
Same Redis lock mechanism used for patient bookings applies uniformly to admin/therapist-initiated bookings.
Appointment time crosses a timezone boundary (traveling patient)
All appointment times stored in UTC with the clinic's IANA timezone attached; clients render in the viewer's local timezone but booking cutoffs are evaluated in the clinic's timezone.
Refund requested after the payment gateway's refund window closes
System flags the transaction for manual reconciliation by an admin rather than silently failing.
Patient deletes their account with active/upcoming paid appointments
Deletion is blocked with a clear message until upcoming appointments are cancelled/completed and any pending payouts settled.
Duplicate webhook delivery from the payment gateway
Idempotency on gatewayPaymentId ensures the second delivery is a no-op, returning 200 without reprocessing.
Therapist availability template changes after slots are already booked
Existing confirmed bookings are honored; only future unbooked slots are recalculated against the new template.
Session token expires mid-form-submission (web console)
Gateway returns 401 TOKEN_EXPIRED; client silently attempts a refresh-token exchange once and retries the original request before surfacing a login prompt.

13. Deployment & DevOps
Each service and the gateway is packaged as an independent Docker image with a multi-stage build (smaller production image, no dev dependencies).
Local development: docker-compose spins up gateway + 4 services + MongoDB + Redis + RabbitMQ with hot-reload.
Production: Kubernetes (or ECS Fargate) with one Deployment per service, HorizontalPodAutoscaler based on CPU/latency, and a managed load balancer in front of the gateway.
CI/CD (GitHub Actions): on PR — lint, type-check, unit tests; on merge to main — build image, push to registry, run integration tests against a staging environment, then manual-approval gated production rollout (rolling update, zero downtime).
Secrets (DB URIs, JWT signing keys, gateway API keys) managed via AWS Secrets Manager / Kubernetes Secrets — never committed to source control.
Each service exposes /healthz (liveness) and /readyz (readiness, checks DB/Redis connectivity) for orchestrator probes.
Database backups: automated daily MongoDB Atlas snapshots with 30-day retention; point-in-time recovery enabled for payments_db.
